## Scope decision and remaining decision

The 2026-10-28 scope decision in #149 authorizes a transaction-aware budget release hook, including project scope, into the existing heartbeat queue/native dispatcher. The queue owns durable intent/receipt state, eligibility, fencing, notification coalescing and release/parking races. Existing startup and scheduler/reaper paths own crash recovery. Do not add a timer, worker, topic, table, route, coordinator registration or held-only claim/write. Do not use executionContinuation for dependency inputs without recovery actions.

This resolves the earlier release/driver ownership question. The revision below fills in that adapter without treating the callback as persistence. One acceptance gap remains: the existing general run/adapter interface cannot prove exactly one external invocation across every process-crash boundary. The precise counterexample and decision package appear below. The original acceptance remains in force pending that decision; this draft is not ready for implementation or approval.

## Queue ownership and durable transitions (proposed)

The normal admission path remains authoritative. Add a private typed result for the trusted native dependency path: admitted with run ID, waiting with a gate, permanently retired with reason, or uncertain/retryable. Keep public wake callers unchanged. Only persisted native dependency provenance grants retention; actor text or caller JSON alone cannot grant it. Other native reasons, including completion review and onboarding handoff, keep their current semantics.

Use the original native intent primary key as the stable input identity. Derive one receipt UUID from that ID in the queue, then insert/adopt it under the existing company-scoped issue lock. The primary key, not a new actor-prefix index, enforces uniqueness. Validate company, issue, target agent, native intent ID, reason and immutable payload binding before adoption. A conflicting ID or several ambiguous legacy receipts is visible repair work, never permission to choose the latest row. Legacy adoption is one bounded transition under the same lock; historical rows with an already linked run remain consumed. Do not mint a new input key; #126 owns the cycle-key repair.

| Durable observation | Queue action |
| --- | --- |
| Original queued; no receipt; current reversible hold | Park the trusted input once using existing deferred state and wait metadata; reserve receipt identity. No run. |
| Parked original; no run; gate unchanged | Read only. No claim, timestamp update, diagnostic increment or new receipt. |
| Parked original; committed release; all gates eligible | Revalidate and claim with existing timestamps; use the reserved receipt in ordinary admission. |
| Receipt deferred with execution ownership | Atomically hand delivery authority to that receipt; original becomes coalesced. Only the receipt can promote. |
| Receipt/run already linked | Adopt the same run and consume the original. Never treat run failure as a new dependency input. |
| Permanent invalidation | Retire once without a run; preserve audit/history. Reassignment relies on its ordinary current-owner producer. |
| Dispatch interrupted before linked run | Re-read reserved receipt and run before retry, through existing reaper. Preserve uncertainty. |

Keep original-to-receipt authority transfer and the run link in the admission transaction. Admission must accept the reserved receipt identity internally; do not insert a diagnostic under another identity first. All final writes, catch/requeue writes and receipt recovery writes match company, input ID, observed status, null run and the exact claim timestamp. Claim takeover also matches the previously observed claimedAt, including null, and the expired threshold. Serialize takeover under the input row lock and use a strictly advancing database claim timestamp so equal application clocks cannot reuse a fence. A losing claimant cannot settle, requeue, reopen or create another receipt. Existing unexpired claims are read-only.

Eligibility inspection before claim is side-effect-free. Calling the current budget getInvocationBlock as that inspection is insufficient: it reconciles through an accounting transaction. Use the budget owner's read-only observation for inspection, then ordinary authoritative admission for reconciliation and revalidation. Where the budget module lacks a reusable pure observation, factor one inside that owner; do not duplicate spend calculations in the queue. The read-only result is not execution authority. Take policy/accounting locks in the existing company-first order before issue/receipt/run locks where required by admission; do not call a second accounting transaction while holding the issue lock. Admission rechecks pause, budgets/exposure, responsible user, company, project, subtree, dependencies, checkout and review under their existing locking contracts. Stop during preparation retains its existing final dispatch gate.

## Committed release and parking race (proposed)

Budget policy stays in budgets. Extend its existing internal hooks with a company-bound scope release notification; do not put budget interpretation in index.ts or the queue. Emit only after a real budget-owned hold transition is durably removed. Agent, project and company branches of resumeScopeFromBudget use the same contract. Policy raise/disable, valid incident override, UTC rollover and accounting correction/settlement reach that contract through their existing reconciliation paths. Unpriced exposure, reservations and another applicable policy can still block. Manual pause is untouched.

The accounting transaction owner accumulates normalized scope invalidations and dispatches them only after the outer transaction is known committed, outside all accounting locks. Nested savepoint success transfers the invalidation to its parent; rollback discards that savepoint's invalidations. Outer rollback emits no release. Merely awaiting withAccountingTransaction on a transaction handle is not an outer commit. An uncertain COMMIT retains the invalidation until existing transaction settlement determines its outcome; no speculative release and no custom timeout. This needs a commit-outcome callback extension at the existing DB work-signal transaction seam, without a new topic or scheduler. Existing intent/settled work signals alone are insufficient because their finally path also publishes after abort. Read committed gates even when a verified callback fires; callbacks do not grant authority.

Install the hook once on the root DB/service lifecycle, so accounting ingestion, direct budgetService calls, reconcileDueBudgetPolicies and startup reconciliation share it. A hook passed only to heartbeat's budgetService instance misses these writers. Dedicated connections share the installed root scope. Independently created clients/replicas have no process-local delivery guarantee: committed rows remain recoverable through their existing reaper. Do not claim arbitrary raw SQL writers trigger normal release. A supported in-process writer that bypasses the transaction seam must be repaired or reported before implementation approval.

The callback requests the existing native dispatcher through the queue, scoped by company plus agent/project as appropriate. Lifecycle onReady requests that same queue path after resumeQueuedRunsForAgent. Agent release cannot drain another company; project release filters by the issue's current project; company release still checks every target gate. Existing execution-wait release owners (checkout/run completion, issue/subtree resume, dependencies, review and configuration) must invoke the same queue entry when they legally change eligibility, retaining their existing authority. No dependency inputs or synthetic recovery rows enter executionContinuation.

The queue owns one in-flight drain per affected scope and a dirty generation. Register the active input before its first eligibility observation. A release during inspection or admission marks that drain dirty. Before committing parking, acquire the existing gate locks and re-read authority; after outer settlement, a generation change causes one bounded immediate recheck of the raced input. Release after parking calls the same path normally. Duplicate notifications merge; unchanged holds stop after that bounded pass. A second release during the follow-up remains pending as a new generation; shutdown cancels callbacks and awaits owned work. No retry timer, passive polling, held-row deadline or recurring drain is added. On crash the in-memory generation is lost, but the durable original/receipt remains the existing reaper's obligation.

This transaction seam is a proposed internal contract, not an implemented or experimentally verified capability. It must be verified with nested savepoint, commit-outcome ambiguity and accounting callers before accepting a runtime patch.

## Existing backstop latency and fairness (proposed)

The concrete existing call chain is index.ts startup orphan_reaping and its heartbeat scheduler runPeriodicRecovery → reapOrphanedRuns → dispatchPendingNativeStatusWakeups. The scheduler interval is max(10 seconds, configured HEARTBEAT_SCHEDULER_INTERVAL_MS), default 30 seconds. Dispatcher staleClaimMs defaults to 60 seconds; the reaper's separate five-minute running-run staleness threshold is not the native input claim threshold. Do not inherit the fork worker's five-second timer.

Preserve the current per-pass limit (default 100, hard cap 500). Within that existing selection replace head-only ordering with a stable requestedAt/ID keyset cursor, scoped to the drain. Read a bounded page, skip held-only rows without claiming/writing them, advance the cursor and wrap after end. Deferred originals as well as queued/expired claims must be discoverable. Do not add another scan, increase tick frequency, or reset the cursor on every duplicate signal. Retained terminal history is excluded. Event-driven drains can consume bounded pages with an in-process continuation of that active request; existing periodic backstop advances one bounded page per eligible tick.

For a fixed set of N pending inputs and page size P, one eligible queued input is visited within at most ceil(N/P)+1 available passes (including wrap); stale-claim recovery adds up to 60 seconds plus the next such visit. With default T=30 seconds this is at most (ceil(N/P)+1)*T after eligibility, plus bounded in-flight pass duration; an unexpired claim adds its remaining expiry. Inserts ahead of the cursor wait for wrap and cannot starve older inputs. Test N>P with held inputs at the head, concurrent inserts and two controllers. Paging observations/cursors are process-local; restart resets them and runs startup recovery. Page work must have measured bounded duration before describing any wall-clock service level.

These are conditional recovery bounds, not unconditional deadlines: suppressed/stopped scheduler, idle drain, warm standby, disabled heartbeat scheduling, unavailable database, or a stuck single-flight recovery chain can postpone the next available pass indefinitely. The existing disabled-scheduler branch only sweeps sandbox cleanup. No new timer or wake capability repairs that here. Normal local committed release still dispatches with periodic ticks frozen; crash recovery requires a resumed existing recovery driver. Report these operating preconditions in tests and operator evidence.

## Precise remaining gap: external invocation after crash

The fresh upstream source establishes a counterexample to the unqualified one-invocation acceptance:

- [legacy-controller-lease.ts:29](https://github.com/paperclipai/paperclip/blob/b14e1ecaf85ce6eafa05125f1b539e3ac7f32022/server/src/services/legacy-controller-lease.ts#L29), legacyControllerClaim/renewLegacyControllerLease, stores preparing and then dispatching on heartbeat_runs; [heartbeat.ts:2785](https://github.com/paperclipai/paperclip/blob/b14e1ecaf85ce6eafa05125f1b539e3ac7f32022/server/src/services/heartbeat.ts#L2785) calls assertOwned("dispatching") before runtime dispatch.
- heartbeat/runtime-execution.ts invokes adapter.execute with runId. The adapter interface in packages/adapter-utils/src/types.ts has execute(ctx), but no universal atomic acknowledge/deduplication contract with the database.
- [server/src/adapters/http/execute.ts:30](https://github.com/paperclipai/paperclip/blob/b14e1ecaf85ce6eafa05125f1b539e3ac7f32022/server/src/adapters/http/execute.ts#L30) calls onDispatch immediately before guardedHttpAdapterFetch. runId is a JSON payload field; no mandatory endpoint-side idempotency or durable request-status query exists.
- [heartbeat/recovery.ts:2414](https://github.com/paperclipai/paperclip/blob/b14e1ecaf85ce6eafa05125f1b539e3ac7f32022/server/src/services/heartbeat/recovery.ts#L2414), restartInterruptedBeforeDispatch/shouldRetry, safely retries legacy preparation interrupted before dispatch, but does not make uncertain dispatch atomic. Native observed ownership can instead remain blocked as observed_owner_unverified. Existing native result recovery is not a proof for every legacy adapter.

Consider two executions with the same committed running/dispatching run and linked input/receipt. In A the host crashes just before the HTTP call; external invocation count is zero. In B the endpoint accepts the call and the host crashes before recording its response; count is one. A durable intent, receipt UUID or claim fence cannot distinguish these observations. Replaying may invoke twice in B; declining replay may leave zero in A. Process identifiers and controller expiry do not prove remote execution stopped. Even a preparing retry may involve a later run under existing recovery policy; one logical dependency delivery must not be confused with one universal runtime attempt.

This limitation exists on both fresh baselines. The fork adds worker/receipt recovery, but does not turn the HTTP endpoint into a transactional participant. It also affects a local adapter call before provider-spawn evidence, so selecting a local adapter without a proven provider protocol does not resolve it.

Decision package for the authorized internal design entry:

| Option | Effect |
| --- | --- |
| Preserve universal exactly-one invocation through arbitrary crash | Requires a separately designed adapter/provider idempotency or durable reattachment/acknowledgement contract. Current scope cannot promise it. No such capability is authorized here. |
| Distinguish delivery from execution uncertainty | Candidate recommendation for adjudication: require one durable dependency admission owner and no duplicate admission; require one invocation for normal/repeated release and proven pre-dispatch recovery. After ambiguous external dispatch, preserve existing visible uncertainty and governed recovery instead of promising automatic exactly once. This changes acceptance and is not applied by this draft. |
| Restrict accepted runtime coverage | Name exact adapters and prove their end-to-end dedup/reattachment protocol with crash tests. No supported adapter is assumed qualified from its name or runId parameter. |

Keep the original acceptance unchanged until the decision is recorded in #149. Do not submit this version as an implementable approved plan. CTO must decide the accepted invocation semantics or commission the missing provider contract through the authorized scope route. No external discussion or runtime work is initiated by this document.
